# Slice 1 — Readable vote descriptions

Epic: "Make the current Congress genuinely useful" (`.claude/current-work.md`, Phase A)
Written: 2026-09-18 · Status: **approved 2026-09-18** — both open questions resolved (see Resolutions at the end)

### Title

Parse and display plain-English roll-call descriptions

### Problem

577 of the 1,414 roll calls in the database have no linked bill, so every surface
that renders them shows only the bare procedural question: "On the Nomination"
(201 rows), "On the Cloture Motion" (200), "On the Amendment" (97), "On the
Motion" (50). A visitor cannot tell *who* was being confirmed, *what* cloture was
being invoked on, or *which* amendment was at stake.

Chuck Grassley's profile (`/members/G000386`) currently shows nine of his twelve
most recent votes as content-free rows. The member profile is the page the epic's
goal names, so this is the blocking defect for the product.

The plain-English text is already inside the XML that `scripts/sync-votes.ts`
downloads and then throws away. Verified against live sources on 2026-09-18:

- `vote_119_1_00300.xml` (cloture on a nomination) carries
  `vote_document_text` = "Stephen Vaden, of Tennessee, to be Deputy Secretary of
  Agriculture" and `vote_result_text` = "Cloture Motion Agreed to (48-45)".
- `vote_119_1_00568.xml` (amendment) carries `vote_document_text` = the
  amendment's purpose sentence and `amendment.amendment_to_document_number` =
  "S. 2296", which is the parent bill the vote is currently not linked to.
- `clerk.house.gov/evs/2025/roll300.xml` carries `vote-desc` = "Enhancing
  Stakeholder Support and Outreach for Preparedness Grants Act".

No new API, no new source, no new rate-limit exposure.

### Acceptance criteria

**Schema**

- [ ] `roll_calls` gains exactly two columns in `db/schema.ts`: `description text`
      (nullable) and `result_text text` (nullable). No other column, table, index
      or constraint changes.
- [ ] A new additive migration exists under `drizzle/` (generated by
      `npm run db:generate`, not hand-written) containing only
      `ALTER TABLE "roll_calls" ADD COLUMN …` statements, and `drizzle/meta/_journal.json`
      is updated by the generator.
- [ ] `db/schema.test.ts` asserts both new columns exist on `roll_calls` and that
      `notNull` is `false` for each.
- [ ] `npm run db:migrate` applies cleanly against the existing database with no
      data loss; pre-existing rows have `description IS NULL` and
      `result_text IS NULL` until re-synced.

**Parsing — shared rules**

- [ ] `lib/votes.ts` exports a pure text-normalizing helper used by both parsers.
      Given a raw XML value it returns a trimmed string with internal whitespace
      collapsed, or `null` when the value is absent, empty, the literal string
      `"undefined"`, or a source filler phrase.
- [ ] The filler set is matched case-insensitively after trimming and stripping a
      trailing period, and is exactly: `no statement of purpose on file`,
      `no statement of purpose`, `no short title on file`, `no title available`.
- [ ] `ParsedRollCall` gains `description: string | null` and
      `resultText: string | null`. No existing field changes type or meaning.
- [ ] Neither parser ever produces `""` or `"undefined"` for the new fields — only
      a non-empty string or `null`.

**Parsing — Senate (`parseSenateVote`)**

- [ ] `description` is the first of these that the helper resolves to non-null,
      in this order: `vote_document_text` → `document.document_title` →
      `amendment.amendment_purpose` → `vote_title`. If all four are absent or
      filler, `description` is `null`.
- [ ] `resultText` is `vote_result_text` if non-empty, else `null`.
- [ ] `billId` resolution is: the existing document-derived attempt
      (`billIdFor` over `document_type` concatenated with `document_number`) first;
      if that yields `null`, fall back to
      `billIdFor(amendment.amendment_to_document_number, congress)`; if that also
      yields `null`, `billId` is `null`.
- [ ] Both bill-id attempts go through the existing `billIdFor` in `lib/votes.ts`
      (which delegates to `makeBillId` in `lib/ids.ts`). No new bill-string parsing,
      normalization, or regex is added anywhere — `billIdFor` already strips dots
      and spaces, so `"S. 2296"` must be passed to it verbatim.
- [ ] A nomination's `document_type`/`document_number` (e.g. `PN` / `12-43`) still
      resolves to `billId = null`, and an `S.Amdt.`-typed document with a populated
      `document_number` also resolves to `null` from the document path (so the
      amendment path is reached).

**Parsing — House (`parseHouseVote`)**

- [ ] `description` is the first of these that resolves to non-null, in order:
      `vote-desc` → `amendment-author`. If both are absent or empty,
      `description` is `null`. (Verified: `roll250.xml` has an empty
      `<vote-desc></vote-desc>` and `<amendment-author>Smith of New Jersey Part A
      Amendment No. 7</amendment-author>`.)
- [ ] `resultText` is always `null` for House votes — the House XML publishes no
      single result-text string. (Its `<vote-totals>` block belongs to slice 2.)
- [ ] `billId` resolution is unchanged (`legis-num` via `billIdFor`).

**Unit tests (`lib/votes.test.ts`)**

- [ ] New XML fixtures, each a faithful reduction of a real document, cover at minimum:
      1. Senate nomination — `description` = the nominee text from
         `vote_document_text`; `resultText` = "Nomination Confirmed (54-45)";
         `billId` = `null`.
      2. Senate cloture motion (shape of `vote_119_1_00300.xml`) — `description` =
         "Stephen Vaden, of Tennessee, to be Deputy Secretary of Agriculture";
         `resultText` = "Cloture Motion Agreed to (48-45)"; `billId` = `null`.
      3. Senate amendment carrying a parent bill (shape of `vote_119_1_00568.xml`) —
         `billId` = `"s-2296-119"`; `description` = the purpose sentence.
      4. Senate vote with the empty/filler fields — `document_number`,
         `document_title` empty and `amendment_purpose` = "No Statement of Purpose
         on File." — `description` falls through to `vote_title`; plus a variant
         where `amendment_to_document_number` is also empty, asserting
         `billId = null` and `description` still non-null.
      5. Plain House bill vote (shape of `roll300.xml`) — `description` =
         "Enhancing Stakeholder Support and Outreach for Preparedness Grants Act";
         `resultText` = `null`; `billId` = `"hr-4058-119"`.
      6. House amendment vote with an empty `<vote-desc/>` — `description` falls
         back to `amendment-author`.
- [ ] Every one of the 47 pre-existing tests still passes unmodified except where a
      `toMatchObject` assertion is extended to cover the new fields.

**Ingestion (`scripts/sync-votes.ts`)**

- [ ] The `roll_calls` insert writes `description` and `resultText`, and the
      `onConflictDoUpdate` `set:` clause includes both, so re-running the sync
      backfills rows that already exist.
- [ ] The batching behaviour is untouched: `BATCH = 5`, `PAUSE_MS = 400`, and the
      loud warning on failed fetches. No increase in request volume, concurrency,
      or new endpoints.
- [ ] Amendment-derived bill ids flow into the existing `billIds` collection, so
      `upsertBills` creates the parent bill row (with a Congress.gov title, or the
      existing `"${TYPE} ${number}"` placeholder when the API call fails) *before*
      the roll-call insert. A re-sync completes with zero foreign-key violations on
      `roll_calls.bill_id`.
- [ ] Running the sync twice in a row produces no errors and no changed row counts
      (idempotence preserved).

**Re-sync and measured outcome**

- [ ] The 119th is re-synced for both sessions — `npm run sync:votes -- 700 2025`
      and `npm run sync:votes -- 700 2026` — with a re-run after a 5–10 minute wait
      if senate.gov 403s are reported.
- [ ] After the re-sync, `select count(*) from roll_calls where description = '' or
      description = 'undefined'` returns 0.
- [ ] After the re-sync, at least 95% of Senate roll calls in the 119th have a
      non-null `description`, and every one of the 201 "On the Nomination" and 200

- [ ] After the re-sync, the number of Senate roll calls whose `question` contains

**Rendering — the four surfaces**

- [ ] The display fallback is identical everywhere and in this order:
      `bills.title` → `roll_calls.description` → `roll_calls.question`.
      Bill title always wins, so any vote that shows a real bill title today shows
      the same text afterwards.
- [ ] Wherever the primary line is *not* the question, the question still appears as
      secondary text — the question is never dropped from any surface.
- [ ] `/members/[id]` — `getRecentPositions` selects `rc.description`; the bold line
      uses the fallback; the sub-line shows `question · result · date` whenever the
      primary line differs from the question, exactly matching the shape used for
      bill-linked votes today.
- [ ] Homepage carousel — `getRecentVotes` selects `rc.description`; `toCardItem`
      sets `title` via the fallback. The `label` (bill number, or the question with
      a leading "On the "/"On " stripped) is unchanged.
- [ ] `/bills` — `getItems` selects `rc.description`; the bill-less branch sets
      `title` via the fallback. `label`, `category`, `chambers`, `phase` and the
      tally are unchanged. `components/bills-browser.tsx` needs no change beyond
      receiving the new titles.
- [ ] `/votes/[id]` — `getRollCall` selects `rc.description`; `fullTitle` uses the
      fallback; the secondary `<p>{rc.question}</p>` renders whenever
      `fullTitle !== rc.question` (replacing the current `rc.bill_title &&` guard);
      `generateMetadata`'s `subject` uses the same fallback;
      `getOtherVotesOnBill` selects and renders `description ?? question`.
- [ ] When `description` is `null` the UI renders exactly what it renders today — the
      bare question, with no placeholder, no "No description available", and no
      empty element. Absence is expressed by falling back, not by labelling.
- [ ] `roll_calls.result` continues to drive `VoteStatusBadge`, `votePhase` and
      `billPhase`. `result_text` is stored but rendered nowhere this slice.

- [ ] `npm run lint && npm run typecheck && npm test && npm run build` passes.

### Scope

**In**

- Two additive nullable columns on `roll_calls` + the generated migration.
- New fields and fallback chains in `parseHouseVote` / `parseSenateVote`, plus the
  shared text-normalizing helper, all in `lib/votes.ts`.
- Amendment → parent-bill linkage via `amendment_to_document_number`, reusing
  `billIdFor`.
- Writing both new fields in `scripts/sync-votes.ts`, including in the upsert's
  `set:` clause.
- Re-syncing the 119th (both sessions) to backfill.
- Reading and rendering `description` on the four named surfaces.
- Unit tests in `lib/votes.test.ts` and the two schema assertions in
  `db/schema.test.ts`.

**Out** — named so they do not get pulled in

- The multi-Congress schema rework (`jurisdictions`, `congresses`,
  `legislator_terms`, integer PKs). That is slice 13. This slice adds columns to
  `roll_calls` and nothing else.
- Verifying stored positions against the published `<count>` / `<vote-totals>`
  tallies — slice 2. Do not parse those blocks, even though this slice touches
  neighbouring XML.
- Re-enabling the nightly cron and the "data current as of" UI — slice 3.
- Bill `summary` / `short_title` population — slice 4.
- Fixing the amendment/bill category precedence in `lib/legislation.ts` — now slice 2, running immediately after this one.
- Any caching change (`force-dynamic`, `revalidate`) — slice 7.
- Any visual redesign, new component, or Tailwind token change — Phase B. New text
  flows through the existing markup.
- Surfacing `result_text` in the UI, and changing `VoteStatusBadge`.
- Nominee enrichment from Congress.gov, PN-number parsing, or a nominations table.
- `lib/ids.ts` changes of any kind — `BILL_TYPES`, `makeBillId` and `parseBillId`
  stay exactly as they are.

**Noted decisions** (made here, not open)

- `description` and `result_text` are two separate nullable columns, not one. They
  answer different questions, `result_text` carries information not derivable from
  `result` (the tally and the majority requirement, e.g. "Amendment Rejected
  (10-88, 3/5 majority required)") which slice 2 will want, and it is free to
  capture now. Nullable because absence is real and must stay distinguishable from
  emptiness.
- House `amendment-author` is used as a second-tier `description` source. It is not
  named in the epic, but `roll250.xml` proves `vote-desc` is empty precisely on
  House amendment votes, and it is the same "text already in the XML" principle.
- Re-syncing with a count of 700 per chamber will also pull in roll calls newer than
  the current 2026-06-11 high-water mark. That is acceptable and expected, but it
  does **not** deliver slice 3 — the cron stays paused and no freshness UI is added.
- The re-sync writes to production Neon. See Open question 2 for who runs it.

### Open questions

**1. Linking amendments to their parent bill silently moves them on `/bills`, and
worsens a bug slice 6 already owns. Which behaviour do we want in the interim?**

`app/bills/page.tsx` branches on `row.bill_id`: rows with a bill id are grouped
into one card per bill and categorised by `categoryForBillType`, which for `s`/`hr`
returns `"bill"`. Rows without one keep their own card and are categorised by
`categoryForQuestion`. So the moment a Senate "On the Amendment" roll call gains a
`bill_id`, it stops being its own card in the Amendments tab and is absorbed into
the parent bill's card. Roughly 97 cards move out of Amendments and into Bills.

This is the same defect slice 6 describes ("65 House amendment votes are filed as
bills because they carry a bill id and `categoryForBillType` wins over
`categoryForQuestion`") — this slice grows it from 65 to ~162.

- **Option A (assumed by the acceptance criteria above):** ship it. The link is the
  point; the amendment is still reachable from the parent bill's "Other votes on
  this bill" list, which this slice makes readable. `/bills` Amendments tab count
  drops by ~97 until slice 6 lands. Zero extra risk to this slice.
- **Option B:** pull a minimal precedence guard forward — classify by the question
  first when the question names an amendment. This fixes the House 65 too, but it
  changes counts across `/bills`, the homepage breakdown table and
  `getPerformance`, which is genuinely slice 6's blast radius.

Recommendation: **Option A**, and move slice 6 up the Phase A order. Flagging rather
than deciding because the acceptance criterion "no regression on the four surfaces"
is user-visible and the user should own the trade.

**2. Who runs the production re-sync, and at what point in the PR flow?**

`DATABASE_URL` points at production Neon; there is no staging database and no local
Postgres. The re-sync is idempotent and additive, but it is a write to live data
from a script whose new columns only exist after `npm run db:migrate` has also been
run against production. `docs/PROJECT.md` §12 says to ask before hard-to-reverse
changes. Needs a call on: (a) does the developer agent run `db:migrate` and the two
syncs itself, or does the owner run them; and (b) does the migration run before the
PR merges (so the preview deploy shows real descriptions) or after. The code can be
written and unit-tested without answering this; only the "measured outcome" criteria
depend on it.

## Resolutions (orchestrator, 2026-09-18 — these are decisions, not suggestions)

**Open question 1 → Option A.** Ship the amendment→parent-bill linkage as specified.
The ~97 cards leaving the `/bills` Amendments tab is accepted as a temporary
regression. The classification fix has been **moved up to slice 2** and runs
immediately after this slice, so the window is short. Do **not** add a precedence
guard to `lib/legislation.ts` in this slice — it stays out of scope.

**Open question 2 → the developer runs both, before the PR.** Run
`npm run db:migrate` against production Neon, then the two re-syncs
(`npm run sync:votes -- 700 2025` and `npm run sync:votes -- 700 2026`), so the PR
preview shows real descriptions and the measured acceptance criteria can be verified
for real. Two things to be aware of:

- This also ingests the ~220 roll calls that have accumulated since the 2026-06-11
  high-water mark. That is expected and fine. It does **not** make slice 3 done —
  the cron stays paused and no freshness UI is added.
- The migration is additive and nullable, so existing reads cannot break. If a sync
  reports senate.gov 403s, wait 5–10 minutes and re-run; it is idempotent.

Record the before/after counts in the PR description as the spec requires.
